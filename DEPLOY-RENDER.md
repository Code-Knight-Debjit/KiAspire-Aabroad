# Deploying to Render (dev/staging)

This is a **dev-hosting** setup, not the production target — production
deployment is HostingRaja/cPanel per `CLAUDE.md` and `DEPLOY.md`. Render is
used here because it's faster to spin up and tear down for development.

The app already satisfies everything Render needs: one Node process,
`app.listen(process.env.PORT)`, `express.static()` serving `frontend/` from
the same process, and Postgres connectivity entirely via `DATABASE_URL`
(SSL already forced on in `backend/knexfile.js`, which matches how Render
Postgres expects connections). No changes were needed to make it deployable
here — `render.yaml` and this doc just make repeat setup fast.

---

## Option A — Blueprint (recommended, fewer manual steps)

1. In the Render dashboard: **New** → **Blueprint**, connect this repo,
   branch `dev`.
2. Render reads `render.yaml` at the repo root and proposes one web
   service (`kiaspire-aabroad-dev`, root dir `backend`). Approve it.
3. Before the first deploy completes, fill in the env vars Render leaves
   blank (`sync: false` in `render.yaml` — Render won't guess secrets):

   | Key | Value |
   |---|---|
   | `DATABASE_URL` | Connection string of your existing Render Postgres instance (**Internal Database URL** if the web service and DB are in the same region — faster and free; **External** if not) |
   | `ADMIN_NAME` | Name for the seeded default admin |
   | `ADMIN_EMAIL` | Login email for that admin |
   | `ADMIN_PHONE` | Phone number for that admin |
   | `ADMIN_PASSWORD` | A password for that admin — dev-only, doesn't need to match production |

   `JWT_SECRET` is auto-generated by the blueprint (`generateValue: true`);
   `JWT_EXPIRE` defaults to `7d`. `PORT` is injected by Render itself — do
   not add it.

4. Deploy. If you're on a **paid** instance type, `preDeployCommand` in
   `render.yaml` runs `npm run migrate && npm run seed` automatically
   before cutover — nothing else to do.

   If you're on the **free** plan, Render skips `preDeployCommand` (it
   requires a paid instance). After the first deploy, open the service's
   **Shell** tab (or `render ssh`, if the CLI is set up) and run:
   ```
   npm run migrate
   npm run seed
   ```
   both are idempotent, safe to re-run after future deploys if you change
   migrations/seeds.

5. Visit the service's `*.onrender.com` URL — you should see the actual
   homepage, not a bare API message.

## Option B — Manual web service (no blueprint)

If you'd rather not use `render.yaml`:

1. **New** → **Web Service**, connect the repo, branch `dev`.
2. **Root Directory**: `backend`
3. **Build Command**: `npm install`
4. **Start Command**: `npm start`
5. **Health Check Path**: `/healthz`
6. Add the same env vars as the table in Option A (all seven —
   `DATABASE_URL`, `JWT_SECRET`, `JWT_EXPIRE`, `ADMIN_NAME`, `ADMIN_EMAIL`,
   `ADMIN_PHONE`, `ADMIN_PASSWORD`).
7. Deploy, then run `npm run migrate && npm run seed` once via the Shell
   tab (same as the free-plan note in Option A).

---

## Notes specific to Render

- **Free plan spins down on idle** and cold-starts on the next request
  (10-60s). Fine for dev; if that's annoying, use a paid instance type
  instead (also unlocks `preDeployCommand`).
- **`cors({ origin: "*" })`** in `backend/index.js` already allows any
  origin, so the `onrender.com` URL works out of the box with no CORS
  changes.
- **`trust proxy: 1`** in `backend/index.js` is correct for Render too —
  Render terminates TLS and proxies over HTTP with one hop, same shape as
  cPanel/Passenger, so the `Secure` cookie flag still gets set correctly.
- If you tear down and recreate the Postgres instance, update
  `DATABASE_URL` in the web service's env vars and redeploy — nothing else
  in the codebase references the DB host directly.
